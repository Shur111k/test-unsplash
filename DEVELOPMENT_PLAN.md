# План розробки тестового завдання

## 1. Джерело та межі аналізу

Вихідний документ з вимогами прочитано перед ініціалізацією проєкту. У ньому описано мінімальну галерею фото, основний функціонал, бонусні задачі, перелік технологій і вимогу опублікувати результат. Нижче окремо позначено **вимоги документа**, **рекомендовані рішення** та **питання на узгодження**. Каркас застосунку вже створено; поточний статус наведено після таблиці етапів.

## 3. Сторінки та маршрути

| Маршрут | Призначення | Дані та дії |
| --- | --- | --- |
| `/` | Головна стрічка | Фото редакційної стрічки, пагінація, перемикання 3/5 колонок, перехід до фото, пошук. |
| `/photos/[id]` | Сторінка одного фото | Фото, автор з посиланням, опис за наявності, лайки, теги, повернення до результатів. |
| `/tags/[tag]` | Фото за вибраним тегом | Галерея за пошуковим словом тега, пагінація, перемикання колонок, перехід до фото. |
| `/search?q=...` | Результати пошуку | Запит, кількість/стан результатів, галерея, пагінація, перемикання колонок. |
| `/register`, `/login`, `/profile` | **Лише бонус** | Реєстрація, вхід, особиста добірка, видалення збереженого. Конкретні маршрути можна уточнити. |

Для списків рекомендовано відображати `page` і `cols` у URL: це робить стан відтворюваним, придатним для SSR і зручним для поширення посилань. Для пошуку в URL також зберігається `q`; для тегів — закодований сегмент `[tag]`. Некоректну сторінку або кількість колонок слід нормалізувати. Перемикач 3/5 відповідає широким екранам; на вузьких екранах реальна кількість колонок зменшується для читабельності.

## 4. Основні user flows

1. Відкрити `/` → побачити фото → перемкнути 3/5 колонок → перейти на наступну сторінку → відкрити фото.
2. На `/photos/[id]` переглянути автора й деталі → натиснути тег → побачити `/tags/[tag]` → перегортати сторінки та відкрити інше фото.
3. Ввести пошуковий запит у спільному хедері → перейти на `/search?q=...` → перегортати результати → відкрити фото → повернутися до пошуку.
4. Обробити порожній пошук, відсутні результати, фото без опису/тегів, невідомий ID фото, помилки API та обмеження кількості запитів.
5. **Бонус:** зареєструватися/увійти → зберегти фото зі стрічки → відкрити профіль → видалити фото зі своєї добірки → вийти.

## 5. API та правила використання Unsplash

| Сценарій | Запит | Що використовує UI |
| --- | --- | --- |
| Головна | `GET /photos?page=&per_page=` | Масив фото, ID, `width`/`height`, `urls`, автор; метадані сторінок із `Link` / `X-Total`. |
| Фото | `GET /photos/:id` | Розширені дані фото: опис, `alt_description`, `tags`, `likes`, автор, посилання. Поля можуть бути порожніми. |
| Пошук | `GET /search/photos?query=&page=&per_page=` | `results`, `total`, `total_pages`. |
| Тег | `GET /search/photos?query=<тег>&page=&per_page=` | Пошукові результати за назвою тега. Це **не гарантована точна фільтрація за тегом**. |

Рекомендований `per_page`: 24, незмінний між переходами; API допускає максимум 30. Ключ доступу передається **тільки із сервера** в заголовку `Authorization: Client-ID ...`; секрети не зберігаються в репозиторії. Серверний адаптер перевіряє параметри, обробляє статуси API, витягує дані пагінації та віддає UI стабільну внутрішню модель. Для SSR не потрібен окремий виклик власного HTTP route handler із серверної сторінки.

Важливі обмеження офіційної документації:

- Демо-режим має ліміт **50 API-запитів на годину**. Потрібні помірне кешування, відсутність зайвих запитів під час перемикання колонок і стан для відповіді `429`. Зображення з `images.unsplash.com` не входять у цей ліміт.
- Відображення фото має використовувати **прямі URL з `photo.urls`**. Для цієї вимоги запропоновано звичайні адаптивні `<img>` з `loading="lazy"`, розмірами/пропорціями та `alt`, без проксіювання чи локального копіювання зображень.
- Біля фото потрібна атрибуція фотографа й Unsplash та посилання на профіль фотографа з `utm_source` і `utm_medium=referral`.
- Якщо згодом додати **завантаження** фото, потрібен виклик `photo.links.download_location`. У вихідному завданні функції завантаження немає.
- API має пошук за словами, а не окремий задокументований endpoint «список фото за довільним тегом». Тому сторінка `/tags/[tag]` у запропонованому варіанті показує пошук за текстом тега; це слід чесно назвати у UI й погодити.
- Офіційні правила Unsplash **забороняють відтворювати основний користувацький досвід Unsplash** і використовувати назву Unsplash у назві власного застосунку. Для цього тестового узгоджено навчальний формат, власний бренд і власний дизайн; за референс беремо лише принцип компонування фото-стрічки. Це дозволяє планувати навчальну реалізацію, але не є автоматичною гарантією відповідності правилам, особливо після публічного деплою. Перед публікацією перевіримо фактичний результат і, якщо він виглядатиме як прямий клон, змінимо подачу або звернемося до Unsplash.

Джерела для перевірки перед стартом: [документація API](https://unsplash.com/documentation), [правила API](https://help.unsplash.com/en/articles/2511245-unsplash-api-guidelines), [пояснення заборони клонів](https://help.unsplash.com/en/articles/2511257-guideline-replicating-unsplash), [атрибуція](https://help.unsplash.com/en/articles/2511315-guideline-attribution), [hotlinking](https://help.unsplash.com/en/articles/2511271-guideline-hotlinking-images).

## 6. Рекомендований стек і архітектура

**Стек для основних вимог:** Next.js App Router + React + TypeScript + CSS Modules на CSS3. Це вкладається в дозволені документом Next.js/React.js і CSS3/SCSS, дає SSR, маршрути та серверний доступ до API-ключа без окремого бекенда. SCSS можна додати пізніше лише за потреби; для такого обсягу звичайного CSS достатньо. HTML5: семантичні `header`, `main`, `form`, `nav`, `figure` та доступні елементи керування.

**Візуальний напрям:** робимо авторський інтерфейс, який виглядає як завершений портфоліо-проєкт. Окремо продумуємо назву й айдентику, виразний перший екран, акуратну типографіку, ритм відступів, світлу/темну палітру лише якщо вона справді підсилює дизайн, приємні стани наведення й фокусу, плавні переходи між режимами галереї та сторінками. Анімації мають допомагати орієнтуватися і не затримувати роботу: плавна поява фото, мікровзаємодії керування, скелетони завантаження, підтримка `prefers-reduced-motion`. Критерій «вау» — цілісність дизайну, швидкість і продумані дрібниці, а не максимальна кількість ефектів. Референс Unsplash стосується насамперед фото-стрічки; окремого слайдера DOCX не вимагає.

**Розподіл відповідальності:**

- `src/app/.../page.tsx`: серверні сторінки; читають `params`/`searchParams`, отримують дані напряму через серверний модуль і повертають HTML з фото.
- `src/lib/unsplash/server.ts`: єдине місце для запитів до Unsplash, ключа, параметрів, кешування, помилок і метаданих сторінок.
- `src/lib/unsplash/types.ts` та `src/lib/photos.ts`: зовнішні типи й мінімальна внутрішня модель фото, нормалізація відсутніх полів.
- `src/components/...`: спільна шапка/форма пошуку, картка фото, masonry-галерея, перемикач колонок, пагінація, атрибуція. Інтерактивними клієнтськими компонентами будуть лише необхідні елементи.
- `src/app/globals.css` та локальні `*.module.css`: базові стилі, брейкпоінти, доступні стани фокусу. Masonry можна почати з CSS columns; перевірити візуальний порядок та навігацію клавіатурою.
- `src/app/loading.tsx`, `error.tsx`, `not-found.tsx`: очікування, помилки й відсутня сторінка.

**Бонусна архітектура:** власний профіль, окреме серверне сховище користувачів і записів `{userId, photoId}`; без зберігання файлів зображень. Реєстрація: зрозуміла форма, перевірка введення, хешування пароля, захищена сесія в cookie, серверна авторизація операцій збереження/видалення. Для опублікованого SSR демо потрібна постійна БД (наприклад, PostgreSQL), а не локальний файл або `localStorage`. OAuth Unsplash не планується.

**Розгортання:** хостинг із підтримкою серверного виконання Next.js (рекомендовано Vercel або перевірений SSR-режим іншого провайдера), змінна середовища для access key, публічний URL. Статичний експорт несумісний із запропонованим SSR та серверним ключем. Репозиторій GitHub і публікація є частиною фінальної здачі, але їх не виконувати до окремої команди.

### Принцип роботи над тестовим

Користувач просить, щоб асистент був не просто «кодогенератором», а працював як **strong middle developer**. У практичному сенсі для цього проєкту це означає:

1. Перед кожним етапом перевіряти вимогу, API-контракт і наявний код, пояснювати обране рішення та його компроміси; не вигадувати можливості Unsplash API.
2. Робити невеликі завершені зміни, не змішувати функціонал, редизайн і рефакторинг без потреби; зберігати зрозумілу структуру, типи й обробку крайових станів.
3. Дбати про UX, адаптивність, доступність, швидкість завантаження, SSR, безпеку ключів і реальну працездатність деплою, а не лише про вигляд у локальному браузері.
4. Перевіряти кожен етап доречними засобами: lint/typecheck/build, цільовими тестами там, де вони перевіряють поведінку, і ручним переглядом потрібних ширин та сценаріїв.
5. Показувати результат етапу, що саме перевірено й які обмеження лишилися; рухатися до наступного етапу після команди користувача.

## 8. Зафіксовані рішення та питання на майбутнє

**Зафіксовано користувачем:** це навчальне тестове для демонстрації навичок; робимо власний виразний дизайн, анімації та максимальну адаптивність; теги реалізуємо через доступний пошук; користувач сам отримає API key і створить GitHub-репозиторій; бонусна реєстрація — проста власна форма й профіль, без Unsplash OAuth; деплой — наприкінці. Асистент працює поетапно з рівнем уваги до якості, очікуваним від strong middle developer.

**Не блокує початок етапу 1, але потребуватиме рішення у відповідний момент:**

1. Перед живою інтеграцією потрібен Unsplash access key; не вставляти його в чат, код або Git, якщо можна безпечно передати через локальну змінну середовища.
2. Перед публічним деплоєм перевірити фактичну відповідність демо правилам API та ліміту запитів. Навчальна мета і власні стилі не скасовують правил провайдера автоматично.
3. Перед бонусом B1 обрати провайдера постійної БД і уточнити мінімальні поля форми. Базова рекомендація: email + пароль, вхід/вихід, профіль.
4. Перед етапом 10 потрібні URL/доступ до GitHub-репозиторію та обраний хостинг. Фінальний деплой має підтримувати SSR і постійну БД, якщо бонуси включені.
5. DOCX не вимагає завантаження фото, лайків від користувача, завантаження власних файлів, фільтрів, нескінченної стрічки або окремого слайдера. Додавати це лише якщо воно підсилить тестове й користувач погодить обсяг.

**Наступна дія:** після окремої команди користувача почати етап 1. До цієї команди код застосунку не створюємо.
